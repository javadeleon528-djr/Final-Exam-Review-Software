## B3 统一错误格式

所有失败响应长得一样，只有一层 `error`：

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "范围草稿已有更新，请查看差异后重试",
    "details": { "current_version": 3, "your_version": 2 },
    "request_id": "req_02"
  }
}
```

四个字段各有分工，缺一个前端就会难做：

| 字段 | 给谁看 | 作用 |
| --- | --- | --- |
| `code` | 程序 | 前端据此决定走哪段处理逻辑，**不要靠匹配 message 文字** |
| `message` | 用户 | 直接显示在界面上，必须是中文人话，不能是堆栈或英文技术报错 |
| `details` | 程序 | 结构化补充：字段名、当前版本号、非法 ID 列表 |
| `request_id` | 查问题 | 用户报「出错了」时，凭这个号在后端日志里定位那一次请求 |

### 四类场景，分别怎么处理

| 场景 | HTTP | `code` | 前端该做什么 | 数据怎么保 |
| --- | --- | --- | --- | --- |
| **输入不合法**（课程名为空、日期早于今天） | 400 | `VALIDATION_ERROR` | 定位到具体输入框标红，`details.field` 告诉你是哪一个 | 用户已填的其它内容全部保留，**不清空表单** |
| **资源不存在**（考试被删了还在操作） | 404 | `VALIDATION_ERROR` | 提示「这场考试已不存在」，给一个回列表的按钮 | 不清空当前页面，让用户能复制走已填内容 |
| **连点两次**（手抖点了两下创建） | 200 / 201 | 无错误 | **不报错**，正常返回第一次的结果 | 靠 `Idempotency-Key` 挡住，第二次直接返回第一次的产物 |
| **两人同时改**（伙伴在另一台改了同样的范围） | 409 | `VERSION_CONFLICT` | 弹窗展示「你的版本 / 服务器版本」差异，让用户选保留哪份 | **绝不静默覆盖**，用户没选之前两边都不动 |

### 连点两次 vs 同时修改，别搞混

这两个都是「撞车」，但处理方式完全相反：

- **连点**：**同一个人**的手误，应该**假装无事发生**——返回第一次的结果，用户看到的是一次成功
- **同时改**：**两个人**的意见不同，必须**打断并让人决定**——不能替用户选

判据也简单：连点靠 `Idempotency-Key`（同一个键 = 同一次意图）；同时改靠 `expected_version`（版本号对不上 = 别人动过了）。

### 错误码清单（9 个，与术语表一致）

| 代号 | 什么时候用 |
| --- | --- |
| `VALIDATION_ERROR` | 输入不合法、找不到资源 |
| `VERSION_CONFLICT` | 别人先改过，你的版本旧了 |
| `SOURCE_UNAVAILABLE` | 网页拿不到正文 |
| `OCR_LOW_CONFIDENCE` | 识别结果不可靠，要人工核对 |
| `ANSWER_KEY_MISSING` | 没有标准答案，无法判分 |
| `GRADING_NEEDS_REVIEW` | 这道题判不了 |
| `AI_TIMEOUT` | 模型超时 |
| `PLAN_INFEASIBLE` | 时间不够，排不下 |
| `STORAGE_ERROR` | 文件或数据库出错 |

## B4 预览与应用是否分离 —— 检查结论

**结论：是分开的，两条独立接口。** 依据设计文档 API-07 与 API-08。

| 环节 | 接口 | 是否写正式计划 | 关键约束 |
| --- | --- | --- | --- |
| 生成预览 | `POST /exams/{examId}/plan-previews` | ❌ 不写 | 只产出 `preview_id` 与差异清单，异步任务 |
| 应用预览 | `POST /plans/{planId}/applications` | ✅ 写新版本 | 必须带 `preview_id` + `expected_version`，后端重新校验全部约束 |

### 为什么必须分开

预览可能算出用户不满意的结果（把重点往后挪了），也可能算出排不下的情况。如果预览直接改正式计划，一次误操作就毁了用户辛苦排的计划，而且没法撤销。

分开之后：**取消预览只删草稿，正式计划毫发无伤。**

### 应用时必须重验

因为预览和应用之间可能隔了几分钟，用户可能已经完成了某个任务、又标了一天不可学、或者手动挪过任务。后端不能盲信预览结果，要重新检查：

1. 考试日前能排完
2. 全天不可学日 0 分钟
3. 部分日期不超可用分钟
4. 已完成 / 已锁定任务不移动
5. 前置依赖不倒置

任何一条不满足，返回 `422 PLAN_INFEASIBLE` 并列出排不进去的任务，**不能假装成功**。
