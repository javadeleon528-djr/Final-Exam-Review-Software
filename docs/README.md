# docs/ 文档地图

这份文件回答一件事：**`docs/` 里每个文件负责什么、什么时候该看它、和谁冲突时听谁的。**

一句话总纲：**`docs/` 下的文件不是一套"设计说明书"，而是 T01 两个任务的交付物清单。** 文件名里的 `A`／`B` 编号就是当初的分工编号——A 是甲的四项产出，B 是乙的四项产出。

---

| 编号 | 文件 | 谁产出 | 它回答的问题 | 属于"给人看"还是"给电脑看" |

## 三、冲突时听谁的（必须记住，按顺位）

| 顺位 | 文件 | 角色 |
| --- | --- | --- |
| 1 | `api-contract.yaml` | **唯一技术事实**。字段名、类型、必填、状态码以它为准 |
| 2 | `glossary.md` | **名词与枚举的唯一解释** |
| 3 | `api-mapping.md` | 页面→接口覆盖证明 |
| 4 | `error-format.md` | 错误处理行为约定 |
| 5 | `example_data.json` | **样例，不是规范**。与契约不一致时，**错的是样例** |
| 6 | 根目录设计文档 | 背景与验收依据。与契约冲突时以契约为准，但冲突要登记 |

**附带层级规则**：样例必须是**接口层视图**，不是数据库行视图。同一概念在 DB 层是独立表、在接口层可能内嵌（如自评：DB 是 `user_point_profiles`，接口是 `Point.self_status`），两层形态不同但都正确。判分歧前先问"这两处是不是同一层"。

## 五、这个目录里没有的（容易误以为有）

- **没有数据模型文档**。表结构只散落在设计文档 §8 的表格里，没有独立的 `data-model.md`，也没有可执行的迁移脚本。写代码时无法查"`plan_tasks` 到底有哪些列"。
- **没有验收清单**。QA-01～QA-14 写在设计文档 §14，没有独立的 `acceptance.md`，测试时容易漏。
- **没有决策记录**。`D01`～`D09` 待确认项在设计文档 §20.2，UI 反复改过的决定（"课程概览"页取消了、"知识点"页并进考试范围了）只存在于对话历史里，没有落成 `product-decisions.md`。**这是本项目最危险的一处欠账**：三个人（甲、乙、Codex）对"要做几个页面"的理解可能不同。

## 六、`工作过程/` 子目录

这里放的是**过程文件**，不是产品文档：它们的寿命只到对应任务结束。

| 文件 | 作用 | 结束后怎么处理 |
| --- | --- | --- |
| `T01-审计方案.md` | 互审剧本：判定词表、三段式时间盒、四步走查脚本、预审疑点清单、任务状态三方案、T02 start gate | T01 关档后作为附录保留（有"当初为什么这么定"的价值） |
| `T01-审计记录表.md` | 互审卷子：6 张表，边审边填 | 填完后结论已回写到契约/术语，本表转为审计证据保留 |
| `T02-任务分工.md` | 同学 A / 同学 B / Codex 三方分工、交接物、最终验收 5 条 | T02 完成后归档 |

**关键区别**：`docs/` 根目录的文件是**长期有效的事实来源**，改它等于改产品；`工作过程/` 里的文件是**一次性作业单**，过期即归档。不要把已裁决的结论只留在过程文件里——必须回写到契约或术语表，否则下次没人会去翻它。
