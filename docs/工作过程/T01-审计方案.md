## 0. 这份文件解决什么

你要的不是"再看一遍文档"，而是**在 30 分钟里判断：这两份东西能不能直接拿去写代码**。

所以审计只有一个判据：

> **换一个人照着文档写前端、另一个人照着文档写后端，联调时会不会必须靠猜？**

凡是要靠猜的地方，就是本次审计的产出。文档写得漂不漂亮不重要，"能不能照着做"才重要。

**一件事先说清**：我先把全部文档对了一遍，已经挑出 **7 条 P0 + 13 条 P1** 疑点，每条都带文件行号（见第 6 节）。所以你的 30 分钟**不是用来找问题，是用来验证问题和找剩下的问题**——把"探索"变成"核对"，效率差三倍。但**必须自己去文件里点开确认**，不许直接把我的清单抄进决议：抄来的问题你讲不清，合会上会被问穿。

## 1. 审计对象与"谁说了算"的顺序

| 顺位 | 文件 | 在审计里的角色 |
| --- | --- | --- |
| 1 | `docs/api-contract.yaml` | **唯一技术事实**。字段名、类型、必填、枚举、状态码，以它为准 |
| 2 | `docs/glossary.md` | **名词与枚举的唯一解释**。中文名、大白话、四态、错误码含义 |
| 3 | `docs/api-mapping.md` | **页面→接口的覆盖证明**。用来查"有没有操作找不到接口" |
| 4 | `docs/error-format.md` | 错误处理的**行为约定**（前端该干什么、数据怎么保） |
| 5 | `docs/example_data.json` | **样例**，不是规范。它和契约不一致时，**错的是样例** |
| 6 | `期末复习助手-技术设计与双人开发计划.md` | **背景与验收依据**。与契约冲突时以契约为准，但冲突本身要登记 |

> 这条顺序现在就定下来，能省掉合会上 80% 的"谁对"之争。样例数据永远是"契约的消费者"，它跟不上契约是正常的——但**每一个跟不上的地方，都意味着一个前端会在第 2 步就卡住的字段**。

**附带一条层级规则（本次审计反复用到，先记住）**：样例数据必须是**接口层视图**，不是数据库行视图。
同一个东西在两层可以有不同形态，而且可以各自都正确——例如"自评"在数据库里是独立表 `user_point_profiles`（设计文档 §8），在接口里内嵌为 `Point.self_status`（契约 L666）。这是一对一扁平化，**不是矛盾**。
所以判分歧前先问：**这两处是不是在同一层？**
- 不同层 → 不是冲突，是"样例拿错了层"，判"冲突"的对象应为**样例的表达层级**，裁决是"把样例改写成接口视图"。
- 同层且不一致 → 才是真冲突，必须选一边，另一处删掉。

## 2. 判定词表：只允许四种结论

审计记录里每条只能用这四个词之一，避免"感觉有点问题"这种无法关闭的条目。

| 判定 | 定义 | 处理动作 | 谁改 |
| --- | --- | --- | --- |
| **一致** | 契约、术语、样例、设计要求相同 | 打勾，不再讨论 | — |
| **缺口** | 应该有的东西没有（缺字段、缺接口、缺状态、缺规则） | 补进契约，记需求 ID | 契约 owner（T01 内两人共同） |
| **冲突** | 两处说法不一样（字段名、状态码、枚举值、语义） | 必须裁决，选定一个，另一处改掉 | 合会当场定 |
| **未定义** | 契约没写默认行为（首次写入版本传什么、非法迁移返回什么） | 定一个默认值写进契约，并写"为什么" | 合会当场定 |

**硬规则**：任何一条判定为"缺口/冲突/未定义"，都必须落到**具体文件 + 具体字段**，并在记录表里写"改成什么"。只写"这里不清楚"= 没审。

## 5. 甲的主线四步走查脚本

每步给：**要发的请求 → 期望的返回 → 必须核对什么 → 这一步最容易卡的地方**。
（JSON 全部取自现有文档，`//` 后面是我的标注，不要抄进代码。）

### Step 1｜建课（照 `example_data.json` 的 `course` 与 `POST /courses`）

```json
// 请求
{ "name": "高等数学", "description": "2026 秋季学期" }
// 返回（契约 201 示例）
{ "data": { "id":"course_1", "name":"高等数学", "description":"2026 秋季学期",
            "created_at":"2026-11-01T08:00:00Z", "archived_at": null },
  "meta": { "request_id":"req_01" } }
```

必须核对：
1. 样例的 `course` 只有 `id/name`，契约 `Course.required = [id, name, created_at]` → **样例缺 `created_at`**（缺字段，小事，但说明样例不是按契约写的）。
2. `meta` 里**没有 version**。那"同名课程怎么办"靠什么判？靠 `409 + DUPLICATE_COURSE + details.existing_course_id`——确认这条链完整（这条是**一致**的，别重复讨论）。
3. 课程名"去掉首尾空格后不能为空"只写在 `description` 里，`minLength: 1` 拦不住 `"   "` → **校验规则在 schema 之外**，需要明确"谁 trim"（**未定义**，P1）。

### Step 2｜确认范围（`scope-draft` → `scope-confirmations`）

```json
// 存草稿 PUT /exams/exam_1/scope-draft
{ "expected_version": 0,
  "items": [ {"point_id":"point_1","included":true,"priority":"normal"},
             {"point_id":"point_2","included":true,"priority":"important"},
             {"point_id":"point_3","included":false,"priority":"normal"} ] }
// 返回 200
{ "data": { "exam_id":"exam_1", "draft_version":1, "included_count":2,
            "important_count":1, "items":[...], "updated_at":"2026-11-01T08:05:00Z" },
  "meta": { "request_id":"req_02" } }
```

必须核对：
1. **样例 `exam_scope` 的每一项没有 `included`**，只有 `{exam_id, point_id, priority}` → 契约里 `included` 是**必填**。样例表达不出"不考"，而"不考"恰恰是范围页最常点的动作。（**冲突**，P0-A07）
2. 样例 `exam_scope` 没有 `scope_version` / `draft_version`——**整条版本链在样例里是断的**。这一步你要能回答："样例里哪一版是已确认的？"答不出，就是样例失真。
3. 自评在样例里是**另一个数组** `user_profiles`，契约里 `self_status` **长在 `Point` 上**（`GET /courses/{id}/points` 直接返回）。
   → 这一条按 §1 的层级规则判：**契约是对的**（接口层就该内嵌），数据库层仍应是独立表（设计文档 §8 `user_point_profiles`），两边其实不矛盾。错的是**样例拿了数据库层的形状冒充接口样例**。
   → 真正要记的风险不是"谁对"，而是：**照样例写前端的甲，会把 `points` 和 `user_profiles` 当成两个请求去合并**，而契约只给了一个请求。判定：**冲突（层级错误）**，裁决：样例重写为接口视图。
   → 顺带一个次生风险（记入 P1）：自评内嵌后，`PUT /points/{id}/self-status` 用的是 `Point.version`，而同一个 `version` 也管着知识点名称等其他字段。改名字和改自评会撞同一个版本号 → 前端会收到莫名 409。
4. 确认动作：`POST /exams/{exam_id}/scope-confirmations`，body 只有 `expected_draft_version`。→ 那"空范围不能确认"是后端拿草稿判断，还是前端拦？返回码是 **400**（设计文档 §7 API-06）还是 **422**（契约 `PlanInvalid`）？（**冲突**，P0-A06）
5. 还有一个洞：`ScopeVersion.items` 只要求 `minItems: 1`，**允许全部 `included:false`** → 一份"确认过但一个考点都没考"的范围可以合法存在。（**缺口**，P1-B04）

### Step 3｜设置不可学习日（`PUT /availability/{date}`）

```json
// 请求
{ "available_minutes": 0, "expected_version": 0 }
// 返回 200
{ "data": { "day": { "date":"2026-11-05", "available_minutes":0, "version":1 },
            "affected_exam_ids":["exam_1"], "affected_task_count":3 },
  "meta": { "request_id":"req_03", "version":2 } }
```

必须核对（这一步是版本问题最集中的地方）：
1. `expected_version` 的 **minimum 是 0**，但 `AvailabilityDay.version` 的 **minimum 是 1**。**从没设置过的日期，第一次传 0 还是 1？** 文档没写。（**未定义**，P0-A03）
2. `data.day.version`（单日版本）和 `meta.version`（全局日程版本）**同时存在**，`POST /plan-previews` 要的是 `availability_version`（全局的）→ 那 `day.version` 给谁用？（**未定义**，P0-A04 的一部分）
3. 样例里是 `"unavailable_days": ["2026-11-05"]`——**字符串数组，没有分钟、没有版本、没有受影响课程**。契约/术语要的是 `availability_day {date, available_minutes, version}`。（**冲突**，P0-A07；三个文档三个名：设计表 `availability_days`、术语 `availability_day`、样例 `unavailable_days`）
4. "全天不可学对所有课程生效""同一天多课程合计不超全局分钟"——**规则写得很清楚，但契约里没有任何字段能验证它**：`affected_task_count` 只是个数，`affected_exam_ids` 只是列举。真正能证明的是 `PlanPreview`（Step 4）。（**一致但依赖下一步**，记在案）

### Step 4｜生成并应用计划（`plan-previews` → `jobs` → `plan-applications`）

```json
// 提交 POST /plan-previews
{ "exam_ids":["exam_1"], "scope_versions":{"exam_1":1},
  "base_plan_versions":{"exam_1":0}, "availability_version":1, "strategy":"balanced" }
// 立即 202
{ "data": { "job_id":"job_01", "status":"queued" }, "meta": { "request_id":"req_03" } }
// 轮询 GET /jobs/job_01 → done
{ "data": { "job_id":"job_01", "status":"done",
            "result": { "preview_id":"prev_01", "affected_exam_ids":["exam_1"],
                        "feasible_before_exam":true,
                        "moved_tasks":[{"task_id":"tsk_05","from":"2026-11-02",
                                        "to":"2026-11-04","minutes":45}],
                        "unscheduled_tasks":[] } } }
// 应用 POST /plan-applications
{ "preview_id":"prev_01", "expected_versions":{"exam_1":0}, "availability_version":1 }
```

必须核对（**这一步问题最多，也是你 30 分钟的主战场**）：
1. **预览能不能画出差异表？** 契约里 `moved_tasks` / `unscheduled_tasks` 的元素是 `{ type: object, additionalProperties: true }`——**等于没定义**。只有 `api-mapping.md` 的示例里出现了 `task_id/from/to/minutes`。前端按哪个写？后端按哪个返？（**缺口**，P0-A05，最严重一条）
2. **`feasible_before_exam` 是顶层一个 boolean**，但设计文档 §7 要求的是"**各考试** `feasible_before_exam`"+"**全局日期容量检查**"。两门课同一天抢时间时，一个 boolean 说不了是哪门课不行。（**冲突**，P0-A05）
3. 设计文档还要求预览里有 `unchanged_task_ids`、`reasons[]`、各考试可行性——契约里 `reasons` 有（`string[]`，但没说有哪些固定文案，前端没法分类），`unchanged_task_ids` **没有**。
4. `base_plan_versions` 首次是 **0**（新考试还没有计划），但应用返回的 `plan_versions` 是 `minimum: 1`。→ 从 0 到 1 的这条规则要写出来（**未定义**，和 P0-A03 同类）。
5. "两个版本映射必须恰好覆盖 `exam_ids`"只写在 description 里，**JSON Schema 表达不了**，所以必须有明确错误码；现在**没说是 VALIDATION_ERROR 还是 PLAN_INFEASIBLE**。（**未定义**）
6. `unscheduled_tasks` 非空 = 排不进去。契约里有 `unscheduled_count`（应用返回），但**预览里没有 count**，前端得自己数。小事，记一笔。
7. 撤销：`POST /plan-undo` 用 `change_batch_id`，`expected_versions` 要"恰好覆盖该批次全部考试"，同样只是 description 约束。
8. 样例 `plan_tasks` 只有 `{exam_id, point_id, date, minutes}`：**没有 `id`、没有 `status`、没有 `locked`、没有 `plan_version`**，还多了契约里没有的 `exam_id`。（**冲突**，P1-B02）→ 你的字段对账表会在这里整段对不上，这是"样例没跟上版本化"的直接证据。
9. 顺带一个免费的好用例：样例里那条任务 `minutes: 120`，术语表故事里的默认是 90 分钟/天 → **样例本身就是一条容量冲突数据**。合会上建议把它明确标注为"反例样例"，专门用来测 QA-05。

## 7. 专项：任务状态怎么定（合会 8 分钟这条）

截图里点名要"重点一起确认任务状态"。现状是 **5 个值、2 个不可达**。三个方案，建议当场选：

| 方案 | 内容 | 改动量 | 代价 |
| --- | --- | --- | --- |
| **A 补齐** | 保留 5 值；新增 `POST /plan-tasks/{id}/start`（`todo→in_progress`，幂等）；`PATCH` 允许 `status` 在 `todo/in_progress ↔ cancelled` 显式迁移；`complete` 只接受 `todo/in_progress` | 契约 +1 接口 +1 字段 | 状态机完整，但要写 5×5 迁移表，否则等于没定 |
| **B 收缩（推荐）** | 首版删 `in_progress`，只留 `todo / done / unscheduled / cancelled`。"开始学习"只是前端 UI 状态，不入库 | 术语 4.6 删一行 + 契约 enum 删一个值 + Q2 关闭 | 失去"进行中"跨会话恢复；单机首版可接受，且**不阻碍任何 P0 验收场景**（QA-04/05/06 都用不到它） |
| **C 派生** | 删 `unscheduled`，"未排"由 `date == null` 派生；status 只剩 `todo/done/cancelled` | 契约 enum 删一个 + 加 `date` 可空约束 | 表达最干净，但前端要多写一个派生判断；与 `needs_replan` 语义重叠 |

**判据（照这三条选，别凭感觉）**：
1. 首版有没有"计时/暂停/继续"的验收场景？没有 → 不需要 `in_progress`（选 B）。
2. "取消任务"是不是用户能点的按钮？是 → 必须有 `cancelled` 的写入路径（A 或 B 都要补，B 里就是 `PATCH status`）。
3. `unscheduled` 和 `date:null` 会不会长期同时存在两种真相？会 → 选 C。

**无论选哪个，都要在同一分钟里写进两处**：`glossary.md` 4.6（表格 + 迁移说明）和 `api-contract.yaml` `PlanTask.status`；并把 `glossary.md` Q2 从"伙伴互审"改成"已确认 + 日期 + 理由"。**只改一处等于没改**——这是 T01 最容易反复的地方。
